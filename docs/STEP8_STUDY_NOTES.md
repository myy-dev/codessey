# 8단계 구현 후 면접/학습 개념 정리

8단계는 보너스 과제 중 기본 구현에 적용 가능한 부분을 통합하고, 나머지를 확장 단계로 분리하는 단계이다. 핵심은 기능을 무작정 늘리는 것이 아니라 현재 설계와 잘 맞는 확장만 선택하는 것이다.

## 1. 핵심 개념

- 보너스 과제는 기본 기능을 망가뜨리지 않는 선에서 적용한다.
- 동적 배열은 최소 힙 구현에 이미 통합되어 있다.
- 이진 트리 개념은 힙의 완전 이진 트리 배열 표현으로 연결된다.
- 스택, 큐, 덱은 문서화와 확장 기능 설계에 적합하다.
- BST와 Pub/Sub는 기본 String 저장소와 분리된 확장 주제로 다루는 것이 좋다.

## 2. 통합 가능한 보너스

### 동적 배열

- 최소 힙 내부 저장소로 사용한다.
- capacity 확장과 amortized O(1)을 설명할 수 있다.

### 이진 트리

- 힙을 완전 이진 트리의 배열 표현으로 설명한다.
- 부모/자식 인덱스 계산을 복습한다.

### 연결 리스트 재활용

- LRU 구현에 사용한다.
- Pub/Sub 확장 시 메시지 큐 또는 구독자 버퍼로 재사용할 수 있다.

## 3. 확장 단계로 둘 보너스

### 스택/큐/덱

- 별도 문서에서 개념과 사용 사례를 정리한다.
- CLI history, 메시지 큐, 작업 큐 같은 예시와 연결할 수 있다.

### BST

- 기본 Redis String 기능에는 직접 필요하지 않다.
- 정렬된 키 조회 같은 요구가 추가될 때 활용할 수 있다.

### Pub/Sub

- 네트워크 통신 없이 단일 프로세스 학습 모델로 제한한다.
- 기본 저장소 구현이 안정화된 뒤 `PUBLISH`, `SUBSCRIBE` 명령으로 확장한다.

## 4. 구현 후 설명할 수 있어야 하는 것

- 어떤 보너스는 기본 구현에 통합하고, 어떤 보너스는 분리했는가?
- 기능 확장이 기존 설계를 복잡하게 만들 때 어떻게 판단하는가?
- Pub/Sub가 일반 key-value 저장소와 다른 점은 무엇인가?
- BST가 현재 핵심 기능에 적합하지 않은 이유는 무엇인가?

## 5. 면접 질문 예시

- 요구사항이 늘어날 때 기존 구조를 어떻게 확장하나요?
- 기능을 추가하지 않기로 결정하는 기준은 무엇인가요?
- Pub/Sub와 요청-응답 모델의 차이는 무엇인가요?
- 정렬된 조회가 필요하면 어떤 자료구조를 고려할 수 있나요?

## 6. 자가 점검

- [ ] 보너스 기능이 기본 기능의 복잡도를 과도하게 높이지 않는가?
- [ ] 통합한 보너스가 실제 구현에 의미 있게 쓰이는가?
- [ ] 확장 기능과 기본 기능의 경계가 문서에 명확한가?
- [ ] 다음 확장 작업의 우선순위를 설명할 수 있는가?
