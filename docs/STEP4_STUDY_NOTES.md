# 4단계 구현 후 면접/학습 개념 정리

4단계는 String 명령어를 구현하는 단계이다. `SET`, `GET`, `DEL`, `EXISTS`, `DBSIZE`, `KEYS`는 저장소 엔진의 기본 동작을 검증하는 핵심 명령어다.

## 1. 핵심 개념

- String 명령어는 key-value 저장소의 기본 CRUD를 담당한다.
- 명령어 실행 전 만료 여부를 확인해야 한다.
- 존재하지 않는 키와 만료된 키는 같은 방식으로 다룬다.
- `GET`은 조회 성공 시에만 LRU를 갱신한다.
- `SET`은 기존 값을 덮어쓰며 기존 TTL을 초기화한다.

## 2. 명령별 학습 포인트

### SET

- 새 키와 기존 키 갱신을 모두 처리한다.
- 기존 키 갱신 시 메모리 사용량 차이를 계산해야 한다.
- 성공 시 LRU를 최신 상태로 이동한다.
- 기존 TTL은 제거한다.

### GET

- 만료 확인 후 값이 없으면 `(nil)`을 반환한다.
- 값이 있으면 문자열 응답을 반환한다.
- 성공한 조회만 LRU access로 본다.

### DEL

- 데이터, TTL, LRU, 메모리 상태를 함께 제거한다.
- 없는 키 삭제는 실패가 아니라 `(integer) 0` 응답이다.

### EXISTS, DBSIZE, KEYS

- 조회성 명령도 만료된 키를 고려해야 한다.
- `KEYS`는 현재 구현에서 정렬 요구가 없으므로 저장소 순서 그대로 반환해도 된다.

## 3. 구현 후 설명할 수 있어야 하는 것

- `SET`이 기존 TTL을 지우는 이유는 무엇인가?
- `GET` 실패 시 LRU를 갱신하지 않는 이유는 무엇인가?
- `DEL`에서 여러 내부 상태를 함께 삭제해야 하는 이유는 무엇인가?
- `DBSIZE`와 `KEYS` 전에 만료 키를 정리해야 하는 이유는 무엇인가?

## 4. 면접 질문 예시

- key-value store에서 `SET`과 `GET`의 기본 시간복잡도는 어떻게 되나요?
- 캐시 조회 실패도 access로 볼 수 있나요?
- 삭제 로직을 공통화하지 않으면 어떤 버그가 생길 수 있나요?
- `KEYS` 명령이 실제 Redis에서 위험할 수 있는 이유는 무엇인가요?
