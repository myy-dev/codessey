# 2단계 구현 후 면접/학습 개념 정리

2단계는 저장소 엔진에서 데이터, TTL, LRU, 메모리 사용량을 함께 관리하는 단계이다. 핵심은 자료구조를 따로 구현하는 수준을 넘어, 여러 자료구조의 상태를 하나의 일관된 저장소 동작으로 묶는 것이다.

## 1. 핵심 개념

- 저장소 엔진은 명령어 실행의 중심 계층이다.
- `data`, `expires`, `lru_list`, `lru_nodes`, `expire_heap`, `memory`는 같은 키에 대해 일관된 상태를 유지해야 한다.
- 하나의 키를 삭제할 때 데이터만 지우면 안 되고 TTL, LRU, 메모리 상태도 함께 정리해야 한다.
- 저장소 계층은 자료구조의 세부 구현을 직접 노출하지 않고 명령어 단위 동작을 제공해야 한다.

## 2. 상태 일관성

저장소 구현에서 가장 중요한 질문은 "키 하나가 변경될 때 어떤 상태들이 같이 바뀌어야 하는가?"이다.

예시:

- `SET key value`: `data`, `lru_list`, `lru_nodes`, `memory` 갱신, 기존 TTL 제거
- `GET key`: 만료 확인 후 값이 있으면 LRU 갱신
- `DEL key`: `data`, `expires`, `lru_list`, `lru_nodes`, `memory`에서 모두 제거
- 만료 삭제: 데이터 삭제와 동일하지만 LRU 갱신은 하지 않음
- eviction 삭제: 데이터, TTL, LRU, 메모리에서 제거하고 `evicted_keys` 증가

## 3. 구현 후 설명할 수 있어야 하는 것

- 저장소 엔진이 왜 필요한가?
- 자료구조를 직접 노출하지 않고 저장소 API로 감싸는 이유는 무엇인가?
- 키 삭제 시 어떤 내부 상태를 함께 정리해야 하는가?
- 만료 삭제와 사용자 `DEL`의 공통점과 차이점은 무엇인가?
- `SET`이 기존 TTL을 제거해야 하는 이유는 무엇인가?

## 4. 면접 질문 예시

- 캐시 저장소를 설계할 때 내부 상태 일관성을 어떻게 보장하나요?
- LRU와 TTL이 동시에 있는 시스템에서 키 삭제는 어떻게 처리해야 하나요?
- 저장소 계층과 명령어 파싱 계층을 분리하는 이유는 무엇인가요?
- 하나의 명령이 여러 자료구조를 갱신할 때 어떤 버그가 자주 생기나요?

## 5. 자가 점검

- [ ] 키 삭제 공통 함수를 만들었는가?
- [ ] TTL 만료 삭제, `DEL`, LRU eviction이 같은 정리 흐름을 공유하는가?
- [ ] `used_memory`가 실제 저장된 데이터와 일치하는가?
- [ ] 저장소 외부에서 내부 자료구조를 직접 조작하지 않게 했는가?
