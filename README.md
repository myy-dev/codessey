# Linux 시스템 장애 분석 및 트러블슈팅

## 프로젝트 개요 (Project Overview)

- Linux 환경에서 실행되는 `agent-leak-app`의 **메모리 누수/OOM**, **CPU 과점유**, **교착상태(Deadlock)**를 관제 데이터와 로그로 분석하는 프로젝트입니다.
- 장애를 단순 재부팅으로 넘기지 않고, 재현 과정과 객관적 증거를 바탕으로 근본 원인을 추론한 뒤 GitHub Issue 형식의 기술 리포트로 기록합니다.
- **분석 원칙**: 관제 데이터와 로그를 먼저 수집하여 원인 증거를 보존한 뒤 조치합니다.
- **분야**: AI/SW 기초
- **구분**: Linux와 OS
- **학습 시간**: 40시간

## 실행 환경 (Environment)

- **운영체제**: Linux
- **대상 프로세스명**: `agent-leak-app`
- **제공 실행 파일**:
  - `agent-app-leak-x86` (Intel 칩)
  - `agent-app-leak-arm64` (Apple Silicon)
- **권장 환경**: 로컬 Linux 또는 격리된 Docker 컨테이너
- **실행 계정**: `root`가 아닌 일반 사용자
- **사용 도구**: `monitor.sh`, `ps`, `top`, `htop`, `pstree`, `kill` 등 Linux 표준 명령어 및 라이브러리
- **네트워크**: `0.0.0.0:15034` 포트 바인딩 가능 환경

## 장애 유형별 필수 증거

| 장애 유형 | 필수 증거 |
| --- | --- |
| OOM | `monitor.sh`의 메모리 상승 수치, 종료 직전·직후 실행 로그, `Memory limit exceeded` 및 `SELF-TERMINATED` 로그, `MEMORY_LIMIT` 변경 전후 최소 2회 실행 결과 |
| CPU | CPU 사용률 급상승 구간의 `top`·`ps`·관제 결과, `WATCHDOG` 및 `SIGTERM` 종료 로그, `CPU_MAX_OCCUPY` 변경 전후 비교 |
| Deadlock | `ps -ef`의 PID 존재 증거, `top -H` 또는 `ps -L`의 CPU·메모리 정체 증거, `WAITING`·`BLOCKED` 마지막 로그, 스레드 및 락 대기 추론 근거 |

## 이슈 리포트 템플릿

각 장애 리포트는 아래 형식을 사용합니다.

```markdown
# [Bug] {장애 유형} - {한 줄 요약}

## 1. Description (현상 설명)

- 어떤 현상이 발생했는가?
- 언제, 어떤 조건에서 발생했는가?

## 2. Evidence & Logs (증거 자료)

- 재현 절차 (실행 명령, 환경변수, 장애 발생 순서)
- `monitor.sh` 관제 로그 데이터 (수치/그래프/스크린샷)
- 프로그램 실행 로그 중 핵심 구간
- `ps`, `top` 등 시스템 도구 출력 결과

## 3. Root Cause Analysis (원인 분석)

- 수집된 증거를 바탕으로 한 기술적 원인 분석
- 관련 운영체제 동작 원리 설명

## 4. Workaround & Verification (조치 및 검증)

- 조정한 환경변수와 변경 값
- 조치 전후 비교 결과 (수치 또는 스크린샷)
- 근본 해결을 위한 추가 제안 (선택)
```

## 핵심 학습 내용

### 메모리 누수와 OOM

- 프로세스의 메모리 구조와 힙(Heap) 메모리의 역할을 이해합니다.
- 해제되지 않은 데이터가 누적되는 메모리 누수 현상을 관제 수치로 식별합니다.
- 메모리 임계치 초과가 개별 프로세스와 시스템 전체에 미치는 영향을 설명합니다.
- MemoryGuard가 시스템 불안정을 막기 위해 프로세스를 종료하는 과정을 분석합니다.

### CPU 과점유와 시스템 지연

- 특정 프로세스의 CPU 과점유와 시스템 전체 부하를 구분합니다.
- CPU 사용률 급상승이 다른 프로세스의 응답 지연으로 이어지는 원리를 설명합니다.
- Watchdog이 임계치를 기준으로 프로세스에 `SIGTERM`을 보내는 보호 흐름을 분석합니다.

### 교착상태

- 프로세스가 살아 있지만 작업이 진행되지 않는 무응답 상태를 진단합니다.
- 교착상태의 4대 조건인 **상호 배제**, **점유 대기**, **비선점**, **순환 대기**를 설명합니다.
- 식사하는 철학자들 문제(Dining Philosophers Problem)를 통해 교착상태의 발생 구조를 이해합니다.
- 프로세스·스레드 상태와 마지막 로그를 연결하여 락 대기 관계를 추론합니다.

### 기술 리포팅

- 로그와 관제 데이터를 근거로 장애 상황을 육하원칙에 맞게 기술합니다.
- 재현 방법, 증거, 원인, 조치, 검증 결과를 GitHub Issue 형식으로 전달합니다.
- 동료가 같은 장애를 재현하고 판단할 수 있을 정도로 명확하게 기록합니다.
